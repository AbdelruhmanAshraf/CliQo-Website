# نسخ CliQo الاحتياطي واسترجاعه

## النسخة الحالية — 7 نوفمبر 2026

أنشأنا نسخة منطقية لقاعدة الإنتاج، وملفات التطبيق والإعدادات، ثم اختبرنا الاستعادة في مشروع Supabase محلي منفصل. الملف الخارجي مشفر بـAES-256-GCM ومحفوظ في مجلد Google Drive الخاص بـCliQo. مفتاح فك التشفير محفوظ في Mac Keychain فقط:

- خدمة Keychain: `com.cliqo.production-backup`
- الحساب: `production-2026-11-07-final-v2`
- مجلد Drive: `CliQo Production Backups`
- صيغة الملف: `CLIQOENC1` + IV بطول 12 بايت + authentication tag بطول 16 بايت + ciphertext
- رُفع الملف المشفّر على 69 جزءًا مرقمًا بسبب حد نقل الملفات؛ ترتيبها وبصمة الملف الكامل موجودان في ملف `.parts.txt` بجوار الأجزاء، وهو المرجع النهائي للتجميع.
- يوجد في المجلد نفسه ملحق مشفر مستقل `cliqo-recovery-supplement-20261107.enc`، يضم ملفي SQL المختبرين ودليل الاستعادة وأداة الفك و`SHA256SUMS`. بصمته SHA-256: `376c62598ce179752a7ff4c184607b5d8c1ef65eaed2f9d110ee5bc65bc93237`.
- يوجد أيضًا ملف إرشادات وأداة فك مستقلة غير مشفرة في المجلد لتسهيل الوصول للنسختين؛ لا تحتوي الأداة على المفتاح. المفتاح محفوظ في Keychain المعتمد، وفقد الوصول إليه يمنع فك النسخة.

النسخة لا تحتوي على مجلد بيانات Postgres الخام. تحتوي على ملفات dump منفصلة، تركيب Supabase المثبت، إعدادات التطبيق والخادم، وأي ملفات Storage موجودة. لا توجد حاليًا كائنات Storage مسجلة في قاعدة الإنتاج. Mailpit mailbox volume غير مشمول. ملف الإعدادات يحوي أسرار تشغيل، لذلك يجب إبقاء الأرشيف مشفرًا وعدم نسخه إلى Git أو مشاركة رابطه.

## النطاق والإصدارات

- قاعدة الإنتاج PostgreSQL `17.6.1.136`.
- صور Supabase في Compose مثبتة بإصداراتها، ومنها GoTrue `v2.197.0` وStorage API `v1.81.0` وPostgREST `v14.18` وRealtime `v2.143.3`.
- بيانات التطبيق والحسابات والتخزين تُنسخ منطقيًا؛ ملف Compose والإعدادات يحفظان إصدارات الخدمات اللازمة لإعادة تركيب متوافق.
- لا يوجد مخطط `supabase_migrations` في إنتاج CliQo. ملفات الترحيل موجودة ضمن إصدار التطبيق المحفوظ.
- يحتوي `managed-schema.sql` على تعريفات سياسات Storage. عند الاستعادة فوق Supabase مُهيأ نتجنب تطبيق هذا المخطط كاملًا، لذا نعيد السياسات بالملف `restore-storage-policies.sql`. مهمة `pg_cron` ليست ضمن بيانات الـdump، وتُعاد بالملف `restore-postgres-jobs.sql`.

## إنشاء نسخة جديدة

استخدم Supabase CLI `3.0.0`، واتصال قاعدة داخليًا عبر SSH؛ لا تفتح PostgreSQL للعامة. لا تطبع URL الاتصال أو تضعه في سجل الأوامر. أنشئ مجلدًا خاصًا بـ`umask 077`، ثم نفّذ dumps منفصلة:

```sh
npx supabase@3.0.0 db dump --remote="$CLIQO_DATABASE_URL" --file roles.sql --role-only
npx supabase@3.0.0 db dump --remote="$CLIQO_DATABASE_URL" --schema public,app_private --file schema.sql
npx supabase@3.0.0 db dump --remote="$CLIQO_DATABASE_URL" --schema public,app_private --file app-data.sql --use-copy --data-only
npx supabase@3.0.0 db dump --remote="$CLIQO_DATABASE_URL" --schema auth,storage,supabase_functions --file managed-schema.sql
npx supabase@3.0.0 db dump --remote="$CLIQO_DATABASE_URL" --schema auth,storage,supabase_functions --file managed-data.sql --use-copy --data-only
```

انسخ ملفات إعداد Compose وبيئة الإنتاج وإصدار التطبيق ومسار Storage الفعلي في حزمة واحدة، مع إيقاف الكتابة أو استخدام snapshot متسق لبيانات Storage. لا تنسخ مجلد بيانات Postgres الخام مع dump منطقي في نفس إجراء الاسترجاع. اشمل ملفات Storage الثنائية إن وُجدت؛ قاعدة البيانات وحدها لا تعيدها.

قبل الرفع، احسب بصمات الملفات، أنشئ أرشيفًا مشفرًا بـAES-256-GCM، واحفظ مفتاحه خارج الأرشيف في خزنة مستقلة. ارفع الملف المشفر فقط إلى Drive، ثم نزّله مجددًا وتحقق من البصمة وفك التشفير قبل حذف النسخة المؤقتة غير المشفرة. احتفظ بسجل يذكر الملفات والإصدارات والنتيجة من دون بيانات عملاء أو أسرار.

## الاسترجاع

1. نزّل كل الأجزاء المرقمة وملف `.parts.txt` والملحق المشفر من Drive. أعد جمع الأجزاء بالترتيب المبيّن وتحقق من بصمتي الملف الأصلي والملحق. اجلب المفتاح من Keychain من دون طباعته أو وضعه في سجل. إذا عرض macOS نافذة سماح للوصول إلى Keychain، اسمح لأداة `security` بالقراءة. استخدم `decrypt-backup.mjs` لفك كل ملف والتحقق من authentication tag داخل مجلد خاص، ثم تحقق من `SHA256SUMS` داخل الملحق.
2. جهّز بيئة معزولة بإصدارات Compose المحفوظة، من دون منافذ عامة أو اتصال بإنتاج أو بيانات SMTP/OAuth حقيقية. ابدأ خدمة `db` وحدها، وانتظر `healthy`، ثم شغّل `/docker-entrypoint-initdb.d/migrate.sh` داخل الحاوية. صورة Postgres المحفوظة لا تشغّل ملفات التهيئة الموجودة داخل المجلدات الفرعية تلقائيًا؛ هذا السكربت ينشئ الأدوار والإضافات وترحيلات Supabase الأساسية. بعدها طبّق `roles.sql` مع الحفاظ على تطابق كلمات مرور قاعدة البيانات مع إعداد Compose، ثم شغّل Auth وStorage وREST بالإصدارات المحفوظة وانتظر سلامتها.
3. طبّق dumps بالترتيب التالي بدور فائق الصلاحية، وأوقف عند أول خطأ:

   - `schema.sql`
   - `managed-data.sql`
   - `app-data.sql`
   - `restore-storage-policies.sql`
   - `restore-postgres-jobs.sql`

   استخدم ملفي SQL من الملحق: نسخة `restore-storage-policies.sql` داخل الإصدار المنشور القديم تحتوي سبع سياسات فقط، بينما الملحق يحتوي الثماني المختبرة، بما فيها قراءة صور الكتالوج. صُححت أيضًا نسخة التشغيل في `/opt/cliqo/website/deploy`، وحُفظت النسخة السابقة على الخادم. لا تطبق `managed-schema.sql` فوق تركيب Supabase أنشأ مسبقًا مخططات `auth` و`storage` و`supabase_functions`. استخدمه فقط عند بناء قاعدة جديدة لا توفر مخطط النظام، وبعد مطابقة إصدارات الخدمات. أعد ملفات Storage إلى volume الاختبار فقط. عند الاختبار المحلي، أنشئ كلمات مرور محلية عشوائية ولا تستورد بصمات كلمات مرور الإنتاج.

4. تحقق من صحة قاعدة البيانات، وأعداد الصفوف وبصمات جداول التطبيق، والسياسات الثمانية ومهمة Cron الواحدة. اختبر RLS بحساب زائر وحساب مستخدم تجريبي: الكتالوج العام مقروء، الملفات الخاصة غير مقروءة للزائر، والعميل لا يرى ملفات عميل آخر. اختبر OTP والبريد والرفع والقراءة داخل بيئة الاختبار؛ لا ترسل طلبًا أو بريدًا إلى عميل من الإنتاج.
5. سجّل الإصدارات، النتيجة، ومدة الاستعادة. احذف مجلد فك التشفير وبيئة الاختبار بعد التحقق، وأبقِ النسخة المشفرة ومفتاحها محفوظين حسب سياسة الاحتفاظ.

## نتيجة اختبار 7 نوفمبر 2026

- أُعيد اختبار النسخة بعد تنزيل أجزاء Drive وتجميعها وفكها والتحقق من AES-GCM و8 بصمات داخلية. بيئة Supabase محلية معزولة استخدمت إصدارات الإنتاج: PostgreSQL `17.6.1.136` وGoTrue `v2.197.0` وStorage `v1.81.0` وPostgREST `v14.18`؛ حاويات DB/Auth/Storage/REST أصبحت سليمة.
- طابقت صفوف 66 جدولًا و228 سجلًا بصمة محتوى dumps حرفيًا، بلا جداول ناقصة أو اختلافات. الأعداد المستعادة: 5 حسابات، 0 طلبات، 6 عائلات منتجات، 22 SKU، 20 قطعة ذكية، 3 دلاء Storage، و0 كائنات Storage. عُيّنت كلمات مرور محلية عشوائية، ولم تُستورد كلمات مرور الإنتاج.
- سجل الترحيلات في التركيب المطابق: Auth عدد 82، Storage عدد 75، و`supabase_functions` صفان؛ أعداد Storage وFunctions تطابق فحص الإنتاج. أُعيد إنشاء سياسات Storage الثماني ومهمة Cron الواحدة.
- اختبار RLS داخل معاملة محلية: الزائر قرأ كائن كتالوج تجريبيًا ولم يقرأ كائنات عميل؛ المستخدم التجريبي قرأ مساره فقط ولم يقرأ مسار مستخدم آخر. قراءات الزائر والمستخدم غير المسجل لجداول العملاء والطلبات أعادت صفرًا. أُلغيت المعاملة بالكامل، ولم تُكتب بيانات إلى الإنتاج.
- Hostinger لم يعرض VPS Backup أو Snapshot وقت الفحص؛ نسخة Drive هذه هي النسخة الخارجية المشفرة الحالية. لم نفعّل جدولًا دوريًا أو سياسة احتفاظ تلقائية.
